# OpenCode v2 support (3.1.12) — backlog

- [RESOLVED] The graphify plugin's `execute.after` hook fires on OpenCode v2 — shown from a real session (171 tool calls) in `~/nexus-test-opencode`: `graphify-out/manifest.json` was rewritten at 14:12:12 UTC, 2 s after the last tool call (14:12:10, a shell call that changed no code), while `graph.json` stayed at 14:07:53. Measured signature: `graphify update . --force` rewrites only `manifest.json` when no code changed, both files when code changed. (`session.shell` doesn't fire the hook, and the assistant's own `opencode run --auto` was blocked by the auto-mode classifier, so the direct marker test never ran.) Cheap way to re-check any time: compare those two mtimes against the last tool call. See `knowledge/patterns/verify-opencode-v2-without-login.md`.
- [BACKLOG] The v2 plugin's coalescing logic (`running`/`queued`) is untested — `node` is a broken nvm lazy-load shim in the dev shell, and the plugin only runs inside OpenCode. Worth a small bun/node test harness if the plugin grows.
- [BACKLOG] `nexus-mcp` closed mid-session on OpenCode v2 — NOT reproduced when the user retested the same evening (nothing in the server was changed), so likely intermittent (e.g. a slow `npm` registry moment behind the 121 s first call). Original details: ("Connection closed: MCP server process exited with code 0", 13:33:39 UTC, 86 ms after an `execute` call to `resolve_package_versions` finished). Root cause NOT found — deliberately left unfixed. Measured: exit code 0 is what the server does when the *client* closes the pipe (0.38 s), so OpenCode dropped it; the server doesn't crash, doesn't idle out (335 s idle fine), and handles the same call sequence fine in isolation. Also measured: `resolve_package_versions` is a sync tool, so the whole stdio server is frozen while it runs (a ping sent at +0 s was answered at +17.8 s) — up to ~150 s worst case (30 s init + 120 s `npm install`); the session's first call ran 121 s, i.e. hit the 120 s timeout. Not shown to cause the closure. A non-blocking fix was TRIED AND REVERTED: both `asyncio.to_thread` and `anyio.to_thread.run_sync` make it worse — with a second request arriving mid-call the server answers one ping, then exits 0 with empty stderr (raw JSON-RPC test, repo venv, mcp 1.28.0), while the original blocking code queues the pings, answers them after the call, and stays alive. So don't "just offload to a thread"; if revisited, test with ≥2 concurrent requests (raw JSON-RPC, not only a client lib) on mcp 1.28 AND 1.30 first. Also note `uvx --from <local path>` ran a stale cached build after a source edit — test local code with the repo's `.venv/bin/python nexus_server.py` or `uv run --directory <repo>`.
- [BACKLOG] OpenCode v1 behaviour of this release is unverified: v2 replaced the v1 binary on the dev machine. v1 paths rest on the docs (`mode: subagent`, `.opencode/agents/`) and are unchanged otherwise.
- [BACKLOG] `nexus sync` writes the graphify plugin into OpenCode projects that opted for codegraph/none (pre-existing for the v1 plugin; now also the v2 one). Codex already follows "only re-add the hook where the project opted in" — OpenCode should too.
- [BACKLOG] `init`/`sync`/`doctor` branch per tool *and* now per OpenCode major — the per-tool spec table suggested in the Codex retro is more overdue before a fourth tool lands.
- [BACKLOG] Agent frontmatter still carries `name:`; OpenCode derives the agent name from the filename and documents no `name` field. Harmless today (all six load on v2.2.5, no warning) — drop it if a later v2 starts warning.
