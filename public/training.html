nexus v4 — preview (pre-release)

Team Training: Build CareSlot Together

A whole team learns nexus v4 the way they'll use it: one shared repository, everyone in their own role, the real commands, and every piece of work reaching main through a reviewed pull request. The project is CareSlot — three made-up clinics that want online booking. It ends the way real projects do: the client changes their mind.

Preview. nexus v4 isn't on PyPI yet. The training runs it as nexus4 (step 1), next to your nexus 3, which stays exactly as it is — nothing to undo afterwards.

The Steps

Pick your role to see only your steps — the commands follow it. Every command block has a copy button.

·
Install Claude Code, git, the GitHub CLI and nexus v4everyone
$ npm install -g @anthropic-ai/claude-code
$ gh auth login
$ alias nexus4="uvx --refresh --from 'git+https://github.com/rcdelacruz/nexus-dev-toolkit@v4-preview' nexus"
$ nexus4 --version   # nexus-dev-toolkit v4.0.0a1
nexus4 is the preview under its own name: your nexus (nexus 3) and your other projects stay as they are, and every run picks up the newest preview by itself. To keep it in new terminals, add the alias line to ~/.zshrc (or ~/.bashrc). In the careslot repository always use nexus4. New to git? Read the git guide first.
$ export TYPESAFE_API_KEY=<your key>   # optional: TypeSafe judgments
Optional — TypeSafe. With a key, nexus asks TypeSafe where it would otherwise guess from keywords: the sections of a doc that doesn't follow the guide, design tokens its rules can't place, and which technologies a doc really uses. Without a key, nexus uses its built-in rules and nothing is sent. Add the line to ~/.zshrc (or ~/.bashrc) and start Claude Code from that terminal. Never put the key in .mcp.json: it's shared in git.
·
Create the team repositorytech lead
On GitHub: a new private repository careslot; invite the team. Then:
$ git clone git@github.com:YOUR-ORG/careslot.git && cd careslot
$ curl -fLO https://v4-preview.nexus-coderstudio.pages.dev/careslot-client-pack.zip && unzip careslot-client-pack.zip && rm careslot-client-pack.zip
$ nexus4 init . --role developer
$ git add -A && git commit -m "CareSlot: client pack, nexus setup" && git push -u origin main
The client pack unzips straight into place: kickoff notes, last quarter's no-show report, a front-desk interview and the team's constraints in docs/requirements/sources/, the designer's design system in docs/designs/design-system/. The client's change request isn't in it — the facilitator sends it later.
Then put your people's GitHub names in .github/CODEOWNERS.nexus-template, rename it to CODEOWNERS, push, and protect main (Settings → Branches): require a pull request and a review from code owners. nexus4 init also writes .gitignore and .graphifyignore: .claude/ stays out of git because everyone's commands depend on their role, graphify-out/ because each person's graph is built on their machine, and the graph skips nexus's bookkeeping, minified files and lock files. The team shares .mcp.json, docs/ and later AGENTS.md; /scaffold adds the stack's own lines to both files.
·
Clone and set up your roleeveryone except the tech lead (done in the setup step)
$ git clone git@github.com:YOUR-ORG/careslot.git && cd careslot
$ nexus4 init . --role product
$ git status   # nothing to commit — your setup stays on your machine
$ claude
Claude Code asks once whether you trust the folder — say yes; nexus has already approved its MCP server and tools, so there's no second question. Every command then looks first, shows a plan, stops for your approval, writes, checks its own work, commits only its own folder and opens the pull request.
·
Write the BRDproduct owner
> /brd docs/requirements/sources/kickoff-notes.md docs/requirements/sources/no-show-report.md docs/requirements/sources/front-desk-interview.md
One BRD for the whole product. Answer its questions from the notes; what nobody knows stays an Open Question with an owner. Merge its pull request, then pull main.
·
Write the PRDproduct owner
> /prd
User stories, functional and non-functional requirements, acceptance criteria — each citing the business rule it serves. Don't split into modules: the architect does that next.
·
Architecture and the epicsarchitect
> /architect careslot — the team's constraints are in docs/requirements/sources/team-constraints.md
Pull main first. The stack on **Choice** lines, ADRs for the big decisions, and the product split into epics — one ADR file each, every story in exactly one. Everything downstream follows your epics.
·
The screensdesigner
> /design careslot --system docs/designs/design-system
One screen per story, epic by epic, from the design system only. Working in Claude Design (Claude Desktop) or Figma Make instead? Export, copy the files into docs/designs/careslot/, commit and open the pull request — no command needed.
·
Day 0 — the scaffoldtech lead
> /scaffold
Once, after architecture and designs are merged: the stack from the Choice lines, exact versions, the theme from the tokens, one template per screen, Docker, CI, AGENTS.md, a passing build gate — no business logic. Merge it before planning. Plan for about an hour: CareSlot's scaffold took about 70 minutes in our own team run. Claude Code asks before writing .pre-commit-config.yaml — approve it.
·
Plan the dev tasks against the codetech lead
> /dev-tasks-planner careslot based on docs/arch-docs/careslot/
One CSV per epic in docs/dev-tasks/careslot/; every task names the files it changes. Hand each developer a task ID.
·
Build one task — four commandsdevelopers, tech lead
> /evaluate BOOK-004   # your task ID
> /plan
> /apply
> /validate
Run them one after the other and read each result before the next. Pick different tasks so you don't collide; the tech lead reviews the pull requests.
·
Send the client's change requestfacilitator
While developers are building, forward the client's email (not in the zip) to the product owner: reminders 2 hours before instead of the day before, and a required reason when a patient cancels.
·
Record the change requestproduct owner, architect, designer
> /change-request CR-001 "Reminder 2 hours before; cancellation reason"
Requirements change first (a changed requirement keeps its ID), then architecture and screens; the architect and designer review. The record lists exactly which IDs changed and which tasks they touch.
·
Re-plan only the affected taskstech lead
> /dev-tasks-planner cr CR-001
Only the rows the change request lists are re-planned; every other task stays exactly as it was.
·
Retroeveryone
Compare with the finished CareSlot example — yours won't match it line for line, and doesn't have to. Where did a pull request bounce, and why? Which Open Question blocked someone? Did the change request touch the tasks you expected?
