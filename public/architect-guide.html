nexus v4 — preview (pre-release)

nexus for Architects

You write the requirements and the architecture that developers build from. nexus gives you commands that follow your team's own templates, check every requirement is covered, and hand developers exactly what changed when a change request comes in — without you touching any code.

Preview. nexus v4 isn't on PyPI yet. Install it from the v4-preview branch: uv tool install --reinstall 'git+https://github.com/rcdelacruz/nexus-dev-toolkit@v4-preview' — or keep nexus 3 as nexus and run the preview as nexus4. Both, plus updating and going back: nexus v4 in the docs.

Who This Is For

Architects, solution designers, and the product owners or business analysts who own the requirements. You work in the project's git repository, but only in docs/. nexus does the git steps for you (branch, commit, pull request) — the git guide covers the rest.

Set Up Once

# 1. install the nexus 4 preview
$ uv tool install --reinstall 'git+https://github.com/rcdelacruz/nexus-dev-toolkit@v4-preview'

# 2. in your copy of the project repository
$ nexus init . --role architect

# 3. open Claude Code there and type /requirements or /architect

Want to keep nexus 3 as your nexus? Skip the install line and run the preview without installing it, under another name:

$ alias nexus4="uvx --refresh --from 'git+https://github.com/rcdelacruz/nexus-dev-toolkit@v4-preview' nexus"
$ nexus4 --version   # then use nexus4 wherever this page says nexus

--role architect installs only /requirements, /architect and /change-request — no developer tools. It also adds the guides to docs/ if they aren't there yet. Check the setup any time with nexus doctor.

Every command runs the same four steps developers use: it looks first, shows you a plan, stops for your approval, writes, then checks its own work against your guide. Nothing is written before you say go, and every command commits only docs/.

/requirements [source]

Imports a BRD, PRD or brief (Markdown, Word or PDF) into docs/requirements/ — one set for the whole product — or writes it with you. Every requirement gets an ID in your project's scheme — e.g. US-014, FR-AUTH-003, NFR-SEC-004, AC-184. Existing IDs are never renumbered. Anything missing from the source (acceptance criteria, a number for "fast") comes back as a question, never invented. Requirement files sitting in docs/arch-docs/ are moved out.

/architect <app>

Reads the product's BRD and PRD and writes or updates docs/arch-docs/<app>/ARCH-…-vN.md (one folder per application — careslot, or core / inventory on a bigger product) with exactly your guide's sections. This is where the product is split into epics: one ADR file per epic, starting with Epic: E001 — <name> and Covers: US-…, FR-…; every story and functional requirement belongs to exactly one epic. Designs and dev tasks (one CSV per epic) follow your epics. The plan shows a coverage map: every requirement ID → the section or ADR that covers it, so nothing is left out. Decisions go on - **Choice**: lines — that's what nexus and developers read as the stack, so a technology that's only mentioned, an "e.g." or a superseded option never ends up in the build.

### Caching
- **Choice**: none — sessions live in SQL Server   ← read as a decision
- **Prior choice (superseded)**: Redis              ← never read as the stack
- **ADR**: ADR-ACME-CORE-E001-009
ADR-CARESLOT-E001-Booking-v1.0.md
Epic: E001 — Booking
Covers: US-002, US-003, US-004, US-005, FR-BOOK-001, FR-BOOK-002, FR-BOOK-003, FR-BOOK-004

## ADR-CARESLOT-E001-002: Prevent double bookings with a database constraint

/change-request CR-004 "…"

A change request goes upstream first: requirements, then architecture, then (via designers) designs. When the docs are updated, nexus reads the git diff and records exactly which IDs changed, were added or removed — and lists the dev tasks that trace to them. The tech lead then runs /dev-tasks-planner cr CR-004, which re-plans only those tasks; every other task stays as it is.

CR-004  Changed: NFR-SEC-003   Added: US-003   Removed: US-002
Affected dev tasks: core/login-tasks.csv — TASK-001 (NFR-SEC-003), TASK-002 (US-002)

Your Guide

docs/arch-docs/ARCHITECTURE-GUIDE.md is your team's template, in plain Markdown: where files go, the section list, the ADR template, your team patterns ("authorization is enforced server-side", "modular monolith first"). Edit it freely — nexus writes it once and never overwrites it. The block at the bottom tells nexus which rules to check and how strictly:

```nexus-guide
{ "kind": "architecture",
  "required_sections": ["Document Metadata", "System Overview", …],
  "stack_section": "Technology Choices",
  "rules": [{"id": "A1", "severity": "BLOCKER", "text": "Every functional requirement is covered"}, …] }
```

The requirements guide (docs/requirements/REQUIREMENTS-GUIDE.md) works the same way and holds your ID patterns. Without a project guide, nexus uses its defaults — the same rules.

What nexus Checks

RuleSeverityWhat it means
A1BLOCKEREvery functional requirement is covered by a section or an ADR
A2BLOCKEREvery required section is present
A3BLOCKERDecisions are on Choice lines; dropped options are marked superseded
A4FIX NOWEvery major decision has an ADR
A5FIX NOWBreaking a team pattern needs an ADR saying why
A6FIX NOWEach client (web, mobile, API) states its stack, consistent with the design
A7FIX NOWEvery NFR has a line in NFR Fulfillment
A8BACKLOGDiagrams are Mermaid, not images

BLOCKER and FIX NOW must be resolved before the pull request is opened; BACKLOG items are listed for later.
