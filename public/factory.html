nexus v4 — preview (pre-release)

nexus as an AI Software Factory

Every team already runs a software factory: requirements become designs, designs become tasks, tasks become reviewed code, and change requests start the loop again. In an AI software factory, agents do most of the building and people move up a level — they decide, approve and review. nexus runs that factory inside your own git repository, from the first business requirement to the reviewed pull request.

Preview. The roles described here are in nexus v4, which isn't on PyPI yet. Run it as nexus4, next to your nexus 3: Try it.

What an AI Software Factory Is

In 2026 "software factory" came to mean a way of building software in which AI agents do most of the work and people design and run the system around them. The clearest current definition is Addy Osmani's in Software Factories, Light and Dark (O'Reilly Radar, September 2026): "many harnessed loops running at once, fed by a queue of work and drained through a review gate into production." Cortex's What is an AI software factory? (June 2026) takes the organisational view: the whole plan–build–production–feedback loop, and the controls around it, which it says are not keeping up.

Governed deployMerged work reaches staging or the team's own cloud through a deploy the platform team controls; agents don't ship to production on their own. "nothing ships without a human approving it" (Encore); you test the whole release in staging and anything off becomes a new issue (coleam00)

Key challenges

  • Review is the bottleneck. Agents open pull requests faster than people can read them. Cortex reports that human review of every PR is "no longer something a team can sustain", and that in its 2026 benchmark incident volume rose along with PR throughput (Cortex).
  • Trusting what nobody read. "The automation is the easy half. Being able to trust a merge you did not read is the hard half" (coleam00/ai-software-factory). Encore makes the same point: writing the code has stopped being the hard part; verifying it and getting it safely to production is (Encore).
  • Isolation. Agents running in parallel collide on shared test runs and databases unless each change gets its own environment (Encore).
  • Context. Agents are only as good as the codebase knowledge, specs and standards they can read, which have to be written down and kept current rather than left to tribal memory (Cortex; Böckeler's "guides").
  • Cost. Agent spend is volatile and can climb faster than teams expect (Cortex); StrongDM's own rule of thumb is at least $1,000 of tokens per engineer per day.
  • Not an "AI factory". An AI software factory builds software. NVIDIA uses "AI factory" for data-centre hardware — a different thing (Cortex).

The ideas behind it

IdeaWhat it meansSource
Humans steer, agents execute Engineers stop typing code and instead design the environment, state the intent and build the feedback loops. OpenAI's team grew from three to seven engineers and merged about 1,500 pull requests in five months with no manually written code. OpenAI, Harness engineering (Feb 2026)
The harness Everything around the model that makes its work trustworthy: guides that steer the agent before it acts (instructions, conventions, specs) and sensors that check after it acts (tests, linters, type checks, AI review), so it can correct itself. Böckeler, martinfowler.com (Apr 2026)
Levels, up to the dark factory Five levels of AI-assisted development, modelled on self-driving cars. At the top, the "dark factory" — named after Fanuc's robot-run plant — is "a black box that turns specs into software". Dan Shapiro (Jan 2026)
Dark in practice StrongDM's factory: specs and end-to-end scenarios drive agents, checked against clones of the services it depends on. Its rules: code must not be written, or reviewed, by humans. StrongDM (Feb 2026)
Lit in practice Stripe's "Minions" start from a Slack message and run in isolated dev machines; over 1,300 pull requests a week contain no human-written code, and each one is reviewed by a person. Stripe (Feb 2026)
Light or dark is a choice per step Dark and lit are the same pipeline with the lights in different places: keep human review where a wrong answer is expensive. Run it all dark, he warns, "and you're stuck tearing everything down four months later." Osmani, O'Reilly Radar (Sep 2026)

The word itself is much older. Hitachi says its Software Factory became the world's first facility dedicated to software in 1969, and "The Software Factory" was the title of a 1975 paper in IEEE Computer. We couldn't find who first applied it to AI agents.

Where nexus sits

nexus is a lit factory for the part of the loop that lives in the repository: plan and build, plus the change requests that feed back into them. On Shapiro's scale it works at levels 3 and 4 — people write the specs, approve every plan and review every pull request. The closest open-source relative, coleam00/ai-software-factory, also starts from a PRD and is also "not a dark factory", but automates the middle: two AI reviewers decide each merge and people judge the result in staging. nexus keeps a person at the plan and at every pull request instead. Five Layers

1. Context — written down, in git, kept current

Agents are only as good as what they can read. In nexus the context is files in the repository, not tribal memory: docs/requirements, docs/arch-docs, docs/designs and docs/dev-tasks, the team's rules in AGENTS.md, lessons in knowledge/, and a code graph (graphify or codegraph) for the blast radius of a change. An MCP server gives every agent the same tools to read them: load_task, ingest_architecture_doc, ingest_design_export, trace_tasks, record_change_request, resolve_package_versions and generate_project_rules.

2. Agents and the harness

The stations are plain Markdown commands that run in Claude Code, OpenCode or Codex. nexus init --role installs only what a role needs: a product owner gets /brd, /prd, /requirements and /change-request and no developer tooling; a developer gets the four EPAV steps plus six reviewer agents (code, database, deployment, performance, monitoring, and a PR verifier).

3. Gates — where a person or a check can say no

  • The plan waits. /plan stops until a person approves it; nothing is written before that.
  • Validation is against the task, not a feeling. /validate checks each acceptance criterion as PASS / FAIL / PARTIAL and sorts issues into BLOCKER, FIX NOW and BACKLOG. A BLOCKER means the task is not done.
  • Every role has its own checks. The product, architect and designer commands validate their documents against a per-project guide — for example, every story cites the business rule it serves, and every design colour is a token.
  • Owners review. nexus init writes a CODEOWNERS template, so a change to requirements, architecture, designs or code waits for the person who owns that folder.

4. Traceability — the record the controls need

Every task row cites the IDs it implements. When a change request arrives, record_change_request reads the git diff of docs/, lists the requirement IDs that were changed, added or removed — in the project's own ID scheme — and trace_tasks returns exactly the task rows that cite them. That is the answer to "what did this change touch, and who reviewed it", written down before any code changes.

5. Learning — the factory improves its own rules

When a step finds a better approach or a trap, it writes it to knowledge/ (retros, patterns, prompts), and the next /evaluate reads it. The factory's rules live in the same repository as its output.

A Real Run: CareSlot

On 23 November 2026 we ran the whole line on the CareSlot example (online booking and reminders for small clinics): one shared git repository, one Claude Code session per role, every step merged through its own branch. The sessions ran headless, so the plans were approved in advance for the run; in daily use a person approves each plan. Times are from the run log.

StepTimeResult
/brd2 minBRD from the client pack, open questions listed for people
/prd5 minPRD with stories, requirements and acceptance criteria
/architect7 min7 epics, architecture doc, ADRs
/design8 min12 screens as frames and tokens
/scaffoldabout 70 minThe skeleton on main: 120 tests passed; one file needed a person's approval
/dev-tasks-planner25 min7 task CSVs, one per epic
Developer: one task—The database rule against double bookings: 4 of 4 acceptance criteria pass on PostgreSQL 17.6; 137 tests passed
/change-request9 min17 requirement IDs changed or added; 19 task rows in 6 files flagged
Re-plan9 minOnly the flagged rows updated; all 7 files (73 rows) pass the checks

A gate that held. The developer's first pass ran before the skeleton had reached main and with no database. /validate reported 0 of 4 criteria run, raised two BLOCKERs, refused to mark the task done and wrote the reason to knowledge/retros/. Once the skeleton was merged and a PostgreSQL 17 was available, the same task passed 4 of 4.

A change request that stayed small. The client asked for one reminder two hours before the appointment, a required reason when a patient cancels, and a monthly count of reasons for the clinic manager. /change-request changed the requirements and architecture first (two new ADRs), listed the affected IDs, and the re-plan touched only the rows that cite them. Questions only a person could answer — for example, which account the clinic manager should use — stayed open questions for the architect, not guesses in code.

What nexus Doesn't Do (Yet)

  • Automatic intake and parallel runs. nexus doesn't pull work from GitHub, Linear or Sentry by itself, and a person starts one task at a time; there is no queue of agents running in parallel.
  • Sandboxes. Agents run in the developer's own checkout, not in isolated environments that nexus creates.
  • Releases. Deployment, staging approvals, feature flags and rollbacks are outside nexus.
  • Production and feedback. Incidents and monitoring don't flow back into the loop by themselves; today a person turns them into a change request.
  • Organisation-wide measurement. nexus checks each task, document and change request. Delivery and reliability trends across teams (DORA-style metrics) belong to other tools.
  • Earned autonomy. The rule is fixed: every plan waits for a person. There are no autonomy levels per team or task type.
  • Service ownership catalogue and agent cost. Ownership is CODEOWNERS in each repository; model spend isn't tracked.
